# Pixel Lab：可复现的第一次图像读写实验

## 项目目标

从一个空项目目录开始，建立可重建的 Python 环境，读取一张图像，记录最基本的程序事实，保存副本；随后建立可解释的 Git 历史、完成三类故障诊断，并让另一环境只按 README 复现。

本项目验证的是 **Stage 0 工具能力**。`shape` 和 `dtype` 在这里是观察值，不要求你已经理解像素矩阵、通道或图像质量。

## 为什么做这个项目

“OpenCV 成功显示一张图”容易被偶然的本机环境和路径掩盖。这个项目要求同时保留输入来源、解释器、依赖、运行命令、失败证据和输出，因此下一位学习者或未来的你才能判断实验是否真的可复现。

## 前置检查

开始前，用自己的话回答：

- 相对路径从哪里解析？
- `sys.executable` 能证明什么？
- 为什么 `image is None` 必须在进入后续处理前检查？
- 你选择手机照片路径还是生成图路径？该路径不能证明什么？
- working tree、staging area 与 checkpoint commit 有什么区别？
- README 必须记录哪些事实，才能区分代码错误和环境漂移？

Pixel Lab 可以在学习早期逐步搭建；进行 Stage 0 最终出口演练前，七个 hard Concept 至少达到 `understood`。Linux 保持 recommended：Windows 路径可以完整通过项目验收，但需完成 Linux 命令对照以满足 Stage 0 的 U 级理解目标。

## 两条等价执行路径

### A. 手机或普通摄像头照片

拍摄任意静物，把原文件复制为 `images/input.jpg`。在 README 记录设备类型、拍摄日期和“未做图像质量评价”。无需购买任何设备，也不需要 RAW 格式。

### B. 程序生成的 PGM 图

没有可用相机时，新建 `src/make_test_image.py`：

```python
from pathlib import Path


def main() -> None:
    width = 64
    height = 64
    pixels = bytes(
        220 if (x // 8 + y // 8) % 2 == 0 else 40
        for y in range(height)
        for x in range(width)
    )
    header = f"P5\n{width} {height}\n255\n".encode("ascii")
    output = Path("images/input.pgm")
    output.parent.mkdir(parents=True, exist_ok=True)
    output.write_bytes(header + pixels)
    print("generated:", output.resolve())


if __name__ == "__main__":
    main()
```

PGM 是简单的灰度图文件；这里使用它只是为了产生无需下载、可重复创建的有效输入。

## 实施步骤

### 1. 建立可读目录

```text
pixel-lab/
├─ images/
├─ output/
├─ src/
├─ evidence/
│  └─ stage-0-exit/
├─ README.md
└─ requirements.txt
```

不要把 `.venv`、真实私密照片或临时缓存当成交付物。

### 2. 创建并记录环境

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install opencv-python
.\.venv\Scripts\python.exe -m pip freeze > requirements.txt
.\.venv\Scripts\python.exe -c "import cv2, sys; print(sys.executable); print(sys.version); print(cv2.__version__)"
```

把最后一条命令与输出复制到 `evidence/environment.txt`。不手工改版本输出。

### 3. 编写输入边界

新建 `src/image_io.py`：

```python
from pathlib import Path

import cv2


def load_image(path_text: str):
    path = Path(path_text).resolve()
    if not path.exists():
        raise FileNotFoundError(f"输入图像不存在：{path}")

    image = cv2.imread(str(path))
    if image is None:
        raise ValueError(f"OpenCV 无法解码图像：{path}")
    return path, image


def save_image(path_text: str, image) -> Path:
    path = Path(path_text).resolve()
    path.parent.mkdir(parents=True, exist_ok=True)
    if not cv2.imwrite(str(path), image):
        raise OSError(f"OpenCV 无法写入图像：{path}")
    return path
```

### 4. 编写入口并观察事实

新建 `src/main.py`：

```python
import sys

import cv2

from image_io import load_image, save_image


def main() -> None:
    input_name = sys.argv[1] if len(sys.argv) > 1 else "images/input.jpg"
    input_path, image = load_image(input_name)
    output_path = save_image("output/copy.png", image)
    _, saved = load_image(str(output_path))

    print("opencv:", cv2.__version__)
    print("input:", input_path)
    print("shape:", image.shape)
    print("dtype:", image.dtype)
    print("output:", output_path)
    print("saved shape:", saved.shape)


if __name__ == "__main__":
    main()
```

手机照片路径运行：

```powershell
.\.venv\Scripts\python.exe src\main.py images\input.jpg
```

生成图路径先运行生成脚本，再指定 `images\input.pgm`。保留完整命令与输出。

### 5. 主动制造失败

运行：

```powershell
.\.venv\Scripts\python.exe src\main.py images\does-not-exist.jpg
```

在 `evidence/bad-path.md` 中先记录预期和实际现象，再写一个假设。用错误中的绝对路径、`Get-Location` 和目录列表验证。修正输入后重新运行有效案例，完成回归。

### 6. 建立小步 Git 历史

至少把“README 与目录”“环境记录”“有效图像输入”“显式失败处理”“Stage 0 证据索引”分成五次单一目的的 commit。每次先检查 `git status`、`git diff` 和 `git diff --staged`。最终有效/坏路径回归通过后，把 `git log -1 --oneline` 的结果写入 `evidence/stage-0-exit/checkpoint.txt`。

### 7. 完成 Stage 0 出口演练

在新的项目副本或干净工作目录中，从 checkpoint 开始计时。不得借用原 `.venv`，只依据 README：

1. 30 分钟内创建虚拟环境、安装依赖、生成或准备输入、运行有效案例和坏路径案例。
2. 保存 `cwd`、`sys.executable`、Python/OpenCV 版本、输入来源、输出位置和总耗时。
3. 完成三张故障卡：不存在路径；一个可重复的 Python 异常；使用错误解释器或缺少依赖。每张都要有假设、验证、修复与正常案例回归。
4. 用 `git log --oneline --decorate --graph` 与两个实际 diff 解释项目如何演进，以及哪个 commit 是本次 checkpoint。
5. 画出“终端 → 进程 → 工作目录 → 解释器 → 包 → 脚本 → 输入/输出”的运行时关系图。
6. 让另一位初学者只看 README 复现；若没有交接对象，七天后由自己在新目录盲复现。首次遗漏必须保留在记录中，不能修改 README 后假装第一次就成功。

`evidence/stage-0-exit/index.md` 应把证据逐项关联到 Stage 的五个稳定 criterion ID。Stage 通过仍需相关 Concept 达到各自路线目标，并在首次具备资格至少七天后完成复测；项目文件齐全不会自动授予通过或 mastered。

## 验收与完成标准

逐项检查 frontmatter 的七个 acceptance criterion：

1. 环境能按文字记录重建，不依赖“我电脑上原来就有”。
2. 有效输入的来源、解析路径、`shape`、`dtype` 和输出路径均被记录，保存副本能再次读取。
3. 无效路径快速失败，故障卡包含一个可证伪假设以及正常输入回归。
4. 至少五次单一目的的 commit 与最终 checkpoint 能由 log 和 diff 解释。
5. 路径、Python 异常、依赖/解释器三类故障均完成诊断闭环。
6. 能解释完整运行时关系，而非只复述命令。
7. 另一位初学者或七天后的自己只看 README，能选择手机或生成图路径在 30 分钟内完成干净复现。

Stage 0 增量通过不等于八个 Concept 自动 `mastered`，也不等于跨 Stage 0–2 的 Pixel Lab 已整体完成。每个 Concept 的证据需分别覆盖其必需标准，再由学习者手动确认；Stage 2 仍会扩展数组、通道和批量 I/O 验收。

## Mastery Evidence 证据映射

- **文件与终端**：项目树、两种工作目录运行对比、输入输出关系图。
- **Python 核心**：对入口分支和函数返回值的逐步解释，而非只贴源码。
- **开发环境**：重建记录、解释器与版本输出。
- **模块与异常**：职责分离的模块、有效与无效输入对照。
- **Git**：五次小步 commit、分支练习、diff 解释与 checkpoint hash。
- **调试**：坏路径故障卡和修复后的回归。
- **Linux**：Linux–PowerShell 命令对照；真实 Linux 运行只在追求 mastered 时补充，不阻塞 Stage 0。
- **可复现性**：干净环境限时重建、README 交接、环境漂移诊断和证据边界。

## 复盘与后续复习

完成当天写下最容易被环境掩盖的一处错误。24 小时后不看命令重述整个运行链；首次满足 Concept 与出口证据后等待至少 7 天，再从 checkpoint 在新目录重建环境、换一张输入、执行三类故障中的抽测并更新 `retest.md`。后续 NumPy/OpenCV 学习继续复用本项目，但新增算法证据时要单独验收。
